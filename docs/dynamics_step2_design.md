## 1. 액추에이터 종류 — `motor` (직접 토크)

```xml
<actuator>
  <motor joint="torso_j1" forcerange="-700 700" ctrlrange="-700 700"/>
  ...  <!-- 17개 -->
</actuator>
```

### 왜 `position`이 아닌가

MuJoCo의 `position` 액추에이터는 PD를 내부에서 암시적으로 풀어 수치적으로 더
안정적입니다. 그런데 **중력 보상 피드포워드를 넣을 자리가 없습니다.** 중력을
`body_gravcomp`로 처리하면 중력 토크가 `actuator_force`에서 사라져서, 사용자가
요구한 **"관절별 토크 포화 시간"** 지표가 무의미해집니다. 실제 모터는 중력도
자기 토크로 버팁니다.

`motor` + 명시적 피드포워드를 쓰면 중력·관성·원심력이 전부 `d.actuator_force`에
집계되고 `forcerange`에 걸립니다. 포화 지표가 물리적 의미를 갖습니다.

안정성은 아래 2절의 damping 분리로 확보합니다. 만약 그래도 발산하면
`position` + 별도 중력 토크 집계로 후퇴합니다 (대안 설계, 5절).

### 베이스 처리

2단계에서 베이스는 아직 운동학입니다. 다만 `qpos`를 직접 쓰면 팔이 선회의
원심력·코리올리를 못 느낍니다. 그래서 `base_yaw`에만 **게인이 매우 큰 `position`
액추에이터**를 붙이고 `forcerange`는 걸지 않습니다. 명시적으로 **이상화된 구속**이며
4단계에서 실제 구동·조향 모터로 교체됩니다. 설정 파일에 `idealised: true`로 표시합니다.

## 2. 제어기 구조

```
tau_i = qfrc_bias_i                    # 역동역학 피드포워드 (중력 + 코리올리)
      + kp_i · (q_des_i − q_i)         # 명시적 비례항
      + kv_i · v_des_i                 # 속도 피드포워드
                                       # −kv_i·v_i 는 관절 damping이 암시적으로 담당
```

### damping 분리가 핵심

`kv·(v_des − v)`를 통째로 명시적으로 넣으면 큰 `kv`(최대 1173)에서 불안정해집니다.
대신 **`−kv·v` 부분을 관절 `damping`으로** 넘깁니다. `integrator="implicitfast"`가
damping을 암시적으로 적분하므로 이 항은 **무조건 안정**입니다. 남은 `+kv·v_des`만
피드포워드로 넣으면 수학적으로 동등합니다.

```xml
<joint name="torso_j1" ... damping="1173.29" armature="1.4666"/>
```

### 게인

목표 폐루프 2차 응답: **ωn = 20 rad/s (3.2 Hz), ζ = 1 (임계감쇠)**

```
kp_i = M_ii · ωn²        kv_i = 2 · ζ · M_ii · ωn
```

| 관절 | kp | kv (= damping) |
|---|---|---|
| torso_j1 | 11732.9 | 1173.29 |
| torso_j2 | 4375.1 | 437.51 |
| torso_j3 | 2217.1 | 221.71 |
| L/R_arm_j1 | 493.9 / 492.6 | 49.39 / 49.26 |
| L/R_arm_j2 | 349.6 / 347.7 | 34.96 / 34.77 |
| L/R_arm_j3 | 106.6 / 105.5 | 10.66 / 10.55 |
| L/R_arm_j4 | 133.2 / 132.0 | 13.32 / 13.20 |
| L/R_arm_j5 | 5.76 | 0.576 |
| L/R_arm_j6 | 15.40 / 15.36 | 1.540 / 1.536 |
| L/R_arm_j7 | 5.34 / 5.32 | 0.534 / 0.532 |

ωn = 20 rad/s 근거: 현재 궤적의 최대 관절 속도 사용률이 0.866이고 URDF velocity
한계가 0.9~2.7 rad/s이므로, 지령 궤적의 대역폭은 1 Hz 미만입니다. 3.2 Hz는 그보다
3배 이상 빠르므로 추종 지연이 지배적이지 않습니다. **이 값은 추정값**이며 설정 파일에
`source: estimated`로 들어가고, 2단계 검증에서 ωn ∈ {10, 20, 40}을 비교합니다.

**M_ii는 자세 의존적입니다.** 위 값은 운반 자세 한 점에서 측정했습니다. 2단계에서는
이 고정 게인을 쓰고, 사이클 전체에서 M_ii가 얼마나 변하는지 함께 기록합니다.
변동이 크면 3단계 전에 온라인 재계산으로 바꿉니다.

## 3. timestep — 5 ms → **2 ms** (동역학 모드만)

| | 5 ms | **2 ms** | 1 ms |
|---|---|---|---|
| `kp·dt²` (torso_j1) | 0.293 | **0.047** | 0.012 |
| M_ii 대비 | 1.0% | **0.16%** | 0.04% |
| 32개 실행 벽시계 (추정) | 488 s | **~1,200 s** | ~2,400 s |

2 ms면 가장 뻣뻣한 관절에서도 필요 armature가 M_ii의 0.16%라 물리적 왜곡이
무시할 수준입니다. 3·4단계에서 접촉이 들어오면 1 ms 재검토가 필요할 수 있습니다.

**운동학 모드는 5 ms를 유지합니다.** `reports/baseline_kinematic/`의 동결 결과를
그대로 재현해야 하기 때문입니다. timestep은 모드별 설정값입니다.

## 4. armature 추정 근거 — **데이터 없음, 추정값**

감속비·로터 관성 자료를 확보하지 못했습니다. 따라서 armature는 물리값이 아니라
**명시적 추정값**으로 다룹니다.

두 가지 하한이 있습니다:

1. **수치 안정성**: 명시적 비례항이 안정하려면 `armature ≳ kp·dt²`. 2 ms에서
   최대 0.047 (torso_j1).
2. **물리적 타당성**: 감속기를 쓰는 로봇 관절의 반사 로터 관성은 통상 링크 관성과
   같은 자릿수이거나 그 수 %입니다. **이 비율의 출처는 확인하지 못했습니다.**

채택안:

```
armature_i = max( β · M_ii ,  2 · kp_i · dt² ,  1e-4 )      β = 0.05  (추정)
```

| 관절 | β·M_ii | 2·kp·dt² | **armature** |
|---|---|---|---|
| torso_j1 | 1.4666 | 0.0939 | **1.4666** |
| torso_j3 | 0.2771 | 0.0177 | **0.2771** |
| L_arm_j1 | 0.0617 | 0.0040 | **0.0617** |
| L_arm_j7 | 0.00067 | 0.00004 | **0.00067** |

β = 0.05에 실측 근거는 없습니다. 이 값이 결론을 좌우하지 않음을 보이기 위해
**β ∈ {0.025, 0.05, 0.10} 민감도 시험을 통과 기준에 포함**합니다. 감속기 사양을
확보하면 설정 파일의 한 줄만 바꾸면 됩니다.

`dof_frictionloss`는 2단계에서 **0으로 둡니다** — 무부하 전류 자료가 없어
추정조차 근거가 없습니다. 4단계에서 현장 실측과 대조할 때 함께 도입합니다.

## 5. simulation.py 변경 범위

class Drive:

class KinematicDrive(Drive):   # 현행 동작 그대로. 바이트 단위로 동일해야 함

### 접촉 판정 임계값 — 설계 결정 필요

현행 `validate_contacts()`는 **3 mm 관통을 즉시 예외**로 처리합니다. 운동학에서는
관통이 곧 오류지만, 동역학에서는 소프트 컨택트 솔버가 항상 약간의 관통을 허용하므로
정상 동작에서도 걸립니다. 제안: 모드별 임계값을 설정에 두고, 동역학 기본값은
**솔버의 정상 관통 범위를 측정한 뒤** 정합니다 (2단계 검증 항목).

### 건드리지 않는 것

`ik.py`(경로 생성은 그대로 지령 궤적 생성기로 사용), `perception.py`, `gripper.py`,
`props.py`, weld 기반 잡기.

| # | 항목 | 측정 | 기준 |
|---|---|---|---|

## 7. 설정 파일 구조

Python 3.10이고 `tomllib`/`pyyaml`이 없어 **JSON(표준 라이브러리)**을 씁니다.
주석 대신 항목마다 출처를 구조로 담습니다.

```
config/
├── station.json     # 환경 치수 — 15층 검토 시 여기만 고침
└── dynamics.json    # 동역학 파라미터 — 추정값 표시
```

모든 말단 항목은 같은 모양입니다:

```json
{
  "nesting_pitch": {
    "value": 0.058, "unit": "m",
    "source": "site_measurement",
    "note": "단차 없이 맞물리는 중첩 1개당 증가. 사용자 제공."
  },
  "slot_pitch_y": {
    "value": 0.66, "unit": "m",
    "source": "design_choice",
    "note": "토트 바닥폭이 아니라 후크 팔의 인출 간격이 결정."
  }
}
```

`source` 허용값: `site_measurement` · `official_urdf` · `measured_in_sim` ·
`design_choice` · **`estimated`** · `idealised`

`estimated`와 `idealised` 항목은 로더가 시작 시 **목록으로 출력**하고 보고서에도
기록합니다. 근거 없는 값이 조용히 섞이지 않게 하기 위함입니다.

`poc_sim/layout.py`는 측정값을 `station.json`에서 읽고 파생식(`HANDLE_BOTTOM`,
`SLOTS` 등)은 그대로 유지합니다. **15층 검토 시 바꿀 항목**은 전부 `station.json`에
모읍니다: 팔레트 높이, 토트 치수, 중첩 pitch, 슬롯 pitch, 컨베이어 위치·높이,
운반 자세, 층수 한계.

## 8. 미결 — 승인 전 확인할 것

1. **ωn = 20 rad/s**가 타당한가. 실제 제어기 대역폭을 아시면 알려주세요.
2. **β = 0.05**로 시작해도 되는가. 감속기 사양이 있으면 추정을 건너뜁니다.
3. **동역학 모드 벽시계 ~20분**(32개)을 수용할 수 있는가. 아니면 2단계 검증은
   `--boxes 8`로 줄이고 전체 실행은 단계 종료 시 1회만 돌립니다.
4. **접촉 임계값**을 측정 후 정하는 순서로 괜찮은가.
